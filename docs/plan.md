## Approved choices and scope

The owner accepted the recommendations: preserve players/history; free prototype for approximately 100 users; Google OAuth, with email magic link when its provider is configured; Neon Postgres; browser practice with local heuristics; fixed ranked 10/20 for ten hands; verified identity plus separate placements; forfeit after three consecutive missed decisions or 60 seconds offline, both absent means void; selective folded-card privacy; no seasonal resets; standard inactivity RD growth; Postgres fan-out; exclude simulated bots from the ranked ladder; owner-private unranked history; owner-only administration; WCAG 2.2 AA; local k6, with 500 spectators, p95 action-to-event <=1 second and failures <1% as the approved test target. The intended minimum age is 12 worldwide; legal and parental-consent launch surfaces are deferred, not declared compliant.

The current temporary brand/origin remains in use. Cookies remain host-only behind the same-origin proxy. Do not scope cookies to the shared hosting parent domain. Only variable names are documented; credentials remain outside Git.

The owner supplied the initial admin identity privately; configure it through `ADMIN_EMAILS`, never infer administration from a display name. Google, Neon and email-provider accounts still need setup. Sentry free integration requires project access. A local SQLite file is available for a rehearsal on a read-only backup; it is not assumed to equal the latest production dataset. Actual live import awaits an approved current export.

Free Render can sleep. Implement and test the deadline worker plus bounded catch-up locally, but do not claim an always-on deadline SLA on a sleeping service. Continuous hosting and actual staging tests remain external deployment gates. No purchases or production rollout are authorized by the implementation plan.

## Migration and rollback sequence

- Inventory and back up only an approved SQLite export; record schema version, row counts and checksums privately. Keep original bytes unchanged. Rehearse first using a separate read-only local backup.
- Apply committed Postgres migrations to an empty isolated/staging database. Transform/import with IDs, timestamps, ratings, sessions and live/queue state preserved. Legacy rooms/matches and name collisions need explicit compatibility mappings; no silent data deletion.
- Verify counts, referential integrity, ledger/room consistency and representative JSON histories. Test legacy signing-cookie compatibility without committing signing secrets. Keep old cookie signing configuration until a user safely upgrades their identity.
- Restore a fresh isolated Postgres database from backup and compare hashes/counts. Test previous-to-current migration path, not only empty schema creation.
- Before a real cutover, require approved snapshot, write-freeze plan and rollback owner. Do not dual-write two rating ledgers. Retain original export and deploy artifact.
- Rollback points the previous compatible application at the preserved source/backup only after reconciling any post-cutover writes. Destructive down-migrations are not an automatic rollback strategy. None of these steps will be run on production by this task without explicit approval.

## Remaining gates and risks

- No paid spend; no production data changes. Free host sleep prevents an unconditional continuous worker/SSE SLA.
- About 100 users is not a precise peak concurrency mix. Validate a conservative 100-connected-user local scenario; keep the 500-spectator test as a separate approved stress target, not a capacity guarantee.
- OAuth/email/provider secrets, a current approved data export and actual staging remain unavailable. Locally present SQLite is a rehearsal source, not proof of live-data preservation.
- Worldwide age 12+ adds actual parental-consent/data-handling requirements. Public legal text and underage registration must not be activated merely because an age label exists. No declaration of worldwide compliance.
- Full public deck-seed recomputation conflicts with selective folded-card privacy. Public proof scope must be honest; ZK verifiable shuffle is outside the current implementation unless separately scoped.
- Ready checks, guest-ranked restriction, auto-check, fixed blinds, real routes, local-only practice bots, unranked-history persistence, unique names and inactivity RD growth are intentional behavior changes approved by the work instructions/answers. Document them in each relevant PR description.
- Statistical matchmaking and shuffled stress tests need repeatable seeds and reported assumptions. A random tournament need not terminate within an arbitrary 200-hand session cap.
