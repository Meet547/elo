# Elo architecture

Elo is a play-money Hold’em prototype. The Next.js frontend runs on Vercel. Browser requests use the same origin under `/api`. The frontend server checks mutation origins, limits bodies and forwards cookies and a server-only proxy credential. The Render backend is a second Next.js app generated by `scripts/prepare-backend.mjs` from maintained backend sources and the shared engine. PostgreSQL owns accounts, queue seats, room revisions, ratings and durable records.

## Frontend and backend boundaries

Browser practice owns its own engine state, animations, cards, timers and heuristic opponents. Reloading discards the practice game. It does not send a game situation to the backend or record a ranked result. The frontend also owns keyboard interactions, responsive layouts and the rating chart’s rendering. The chart receives real timestamps and rating values from the owner’s history endpoint.

Private and ranked rooms run the shared engine on the backend. Clients send revision-checked intentions. The backend authenticates the actor, checks the current room and legal action, commits the update and sends a personalized snapshot. Command receipts keep repeated requests from applying an action twice. PostgreSQL notifications drive room and queue streams. Room events can resume by revision while retained, and a new queue stream reads the current assignment.

A worker started with the backend advances persisted deadlines and cleans expired records. It also captures the daily ladder reconciliation. Room reads can catch up due state. A suspended free host resumes processing on wake.

## Routes and user flows

- `/` opens the lobby. A guest can claim a table name or visit `/login` for sign-in. The session cookie resumes the same profile after a reload.
- `/table` starts or resumes the practice game in the current tab. The cash-out receipt stays within the practice route. Practice opponents are local heuristics.
- `/live` creates a room or accepts a six-character invitation. `/live/[code]` restores that room, shows participant-specific cards and receives live revisions. The host prepares the deal after the required players join. Completed private games write owner-only unrated records.
- `/ranked` requires a verified identity and a unique claimed name. The queue uses separate placement and established pools. A pushed assignment opens the ready check at `/live/[code]`. Two confirmations precede the private seed exchange and ten-hand match. The settlement updates both players and their history atomically.
- `/profile` loads the owner’s lifetime recorded totals, recent results and timestamped rating changes. `/leaderboard` reads the real ladder. `/match/[id]` gives authorized participants the recorded results or disclosed hand history.
- `/verify/[handId]` checks public disclosed-card membership. The complete seed transcript and hidden cards stay in restricted audit data. See [fairness rules](FAIRNESS.md).
- `/settings` offers Google account linking where configured, rename, sign-out, export and profile closure. Allowlisted verified administrators can review pair signals and void or reverse a match.
- `/terms` and `/privacy` show the pending approval status of the owner’s notices.

## Data and access

Player IDs remain stable across guest claims and provider linking. Auth credentials are hashed or held in short-lived attempts. Owner histories are filtered by the authenticated session. Public wire results are ranked and exclude reversed outcomes. Private results identify a room instance, which stays distinct from a reusable invitation code. The public fair-hand archive projects only disclosed membership proofs. Separate audit input contains private seeds and deal order.

Rating snapshots freeze at proposal. Terminal settlements and moderation adjustments are durable. Open voids produce zero rating movement. Reversals append compensation and preserve prior rows. See [ratings rules](RATINGS.md) and [operations](OPERATIONS.md).
